# demo03 Web 端重构改造计划

> 依据：《智慧研讨室预约与门禁管理系统 — 可行性分析报告》（`项目更新可行性计划.docx`，2026-10-13，团队 TokenMaxxing）
> 基线代码：`demo03` 当前 `main` 分支（Spring Boot 3.5.14 / JDK 17 / Thymeleaf / MyBatis-Plus 3.5.15 / MySQL 8.0 `db02`）
> 文档定位：本计划是**软件侧的施工图**。文档中"拟""设计"字样的一期基线，在本计划中一律按**硬需求**处理；确无依据处单列在第 10 节待确认清单。

---

## 0. 一页纸结论

| 项 | 结论 |
|---|---|
| 性质 | 不是"加功能"，是**业务内核换代**。现有系统的三个基本假设（任意时段、区间重叠即冲突、审批即终态）都与文档冲突。 |
| 推进方式 | **原地渐进重构**：在原仓库按 9 个阶段替换，每阶段结束可编译、可运行、可回归；不做双模块并行、不推倒重写。 |
| 前端形态 | 保留 Thymeleaf 服务端渲染多页 + 拦截器鉴权，只做**移动端适配**与"ECharts 甘特图 → 2 房间 × 56 单元的 CSS Grid 排期板"的局部替换（沿用 2026-10-20 已定的排期板技术决策）。 |
| 硬件节奏 | 器材未到货，**先交付一个设备模拟器**（同样走 MQTT、同样校验 HMAC 与幂等），真机到货后只换连接参数与驱动层。 |
| 最大技术风险 | ①「待审批不占单元 + 批准时整体回滚」的并发正确性；②95 个存量测试中约 40% 会因状态机变更而失效，需要重建而不是修补；③规则引擎若做成通用 JSON DSL 会失控——必须**参数化而非脚本化**。 |
| 工作量 | 软件侧重构 520 人时。对照文档表 4-2，软件相关工作包合计 720 人时（100+220+160+140+100），差额约 200 人时对应"登录鉴权 / 拦截器 / 日志 / 房间管理"等已有可用代码的复用——这正是"原地重构"相对"从零开发"省下来的部分。 |
| 关键取舍 | 一期**不做**签退、人体感应、候补、能耗、维护模式、信用联评，与文档 1.3 节一致。 |

总量校验：文档表 4-2 为 940 人时 / 容量 960 人时，缓冲仅 20 人时。因此本计划**不新增**文档未列的工作包；凡新增项必须从"可选演示项"里减。

### 3.2 `t_reservation` 改造（核心表）

保留原表名与主键，字段按文档补齐。**删除** `check_in_code` 到独立表（见 3.5 理由说明），**重命名** `reject_reason` → `decision_reason`。

```sql
ALTER TABLE t_reservation
  MODIFY COLUMN reservation_status TINYINT NOT NULL DEFAULT 0
    COMMENT '0待审批 1已通过 2已拒绝 3已取消 5超时释放 6已签到 7已结束（4 已废弃保留不用）',
  ADD COLUMN purpose             VARCHAR(200) DEFAULT NULL COMMENT '用途说明（信用分<70 转人工时必填）',
  ADD COLUMN rule_version_id     BIGINT       DEFAULT NULL COMMENT '判定所依据的规则版本',
  ADD COLUMN decision_path       VARCHAR(30)  DEFAULT NULL COMMENT 'AUTO_PASS/REJECTED_BASIC/MANUAL_PENDING/MANUAL_APPROVED/MANUAL_REJECTED',
  ADD COLUMN hit_rule_codes      VARCHAR(200) DEFAULT NULL COMMENT '命中的规则编号，逗号分隔',
  ADD COLUMN cancel_source       VARCHAR(20)  DEFAULT NULL COMMENT 'USER/TEACHER_OVERRIDE/ADMIN',
  ADD COLUMN approved_by         BIGINT       DEFAULT NULL COMMENT '人工审核人',
  ADD COLUMN approved_at         DATETIME     DEFAULT NULL COMMENT '人工审核时间（用于 24h 办结考核）',
  ADD COLUMN reminded_at         DATETIME     DEFAULT NULL COMMENT '结束前提醒登记时刻（保证只提醒一次）',
  ADD COLUMN closed_at           DATETIME     DEFAULT NULL COMMENT '进入终止态的时刻',
  ADD COLUMN version             INT NOT NULL DEFAULT 0 COMMENT '乐观锁',
  CHANGE COLUMN reject_reason decision_reason VARCHAR(200) DEFAULT NULL COMMENT '拒绝/取消/释放原因',
  ADD KEY idx_slot_scan (room_id, start_time),
  ADD KEY idx_manual_due (reservation_status, approved_at),
  ADD KEY idx_device_display (room_id, reservation_status, start_time, end_time);
```

> **为什么 6/7 而不是 4/6**：`4` 在旧数据里表示「用户取消」。若沿用 `4` 表示「已签到」，任何漏迁移的旧行、任何未及时更新的 SQL，都会被读成"已签到"并**授予开锁权限**——这是安全方向的错误。取用从未出现过的 `6`/`7`，则旧代码读到新值必然落进 `default` 分支（拒绝），失败安全。

### 3.3 `t_reservation_slot`（占用表，新增）

```sql
CREATE TABLE t_reservation_slot (
    id             BIGINT      NOT NULL AUTO_INCREMENT,
    reservation_id BIGINT      NOT NULL COMMENT '关联 t_reservation.id',
    room_id        BIGINT      NOT NULL COMMENT '冗余，供唯一键使用',
    slot_date      DATE        NOT NULL COMMENT '占用日期',
    slot_index     SMALLINT    NOT NULL COMMENT '0..55，对应 08:00 + index*15min',
    PRIMARY KEY (id),
    UNIQUE KEY uk_room_date_slot (room_id, slot_date, slot_index),  -- ★ 并发仲裁靠它
    KEY idx_reservation (reservation_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='有效占用单元（仅已通过/已签到）';
```

**设计要点**

1. **唯一键即锁**。批准时批量插入 N 行；任意一行撞键 → `DuplicateKeyException` → 事务整体回滚。不需要先 SELECT 再 INSERT，天然规避读后写竞争。
2. **终止即删**。拒绝/取消/超时释放/已结束 → `DELETE WHERE reservation_id = ?`。文档 3.2.1 明确"不把历史记录的唯一约束误当作有效资源占用约束"。
3. **只有一种占用状态**。表里出现行 = 该单元被有效占用。没有"占位但已作废"的行，因此不存在脏占位。
4. **展示不读此表**。Gantt/时段网格从 `t_reservation` 按时间范围查，避免占用表被当成视图用。

## 4. 状态机

### 4.1 迁移表（唯一真源，写在 `domain/ReservationStatus` 内）

| 当前态 | 允许动作 | 目标态 | 触发者 | 副作用（必须在同一事务） |
|---|---|---|---|---|
| 待审批 0 | 基础规则不通过 | 已拒绝 2 | SYSTEM | 写 `decision_path=REJECTED_BASIC`、`hit_rule_codes` |
| 待审批 0 | 附加规则自动通过 | 已通过 1 | SYSTEM | 插 slot、发码、`decision_path=AUTO_PASS` |
| 待审批 0 | 转人工后管理员批准 | 已通过 1 | ADMIN | 重检 slot → 插 slot、发码、写 `approved_by/at` |
| 待审批 0 | 管理员拒绝 | 已拒绝 2 | ADMIN | 写 reason、`decision_path=MANUAL_REJECTED` |
| 待审批 0 | 用户取消 | 已取消 3 | 本人 | `cancel_source=USER` |
| 待审批 0 | 开始时刻已过仍未处理 | 超时释放 5 | 定时任务 | 无 slot 可删；通知申请人 |
| 待审批 0 | 教师覆盖（未开始） | 已取消 3 | TEACHER | `cancel_source=TEACHER_OVERRIDE`、撤码、通知 |

**实现方式**：`ReservationStatus.canTransitTo(target)` 静态表 + `updateStatusGuarded(id, from, to, extraWhere)`（`UPDATE ... WHERE id=? AND reservation_status IN (from) [AND version=?]`，返回影响行数，`0` 表示竞争失败）。**禁用** `getById → set → updateById` 的三段式，这正是现有 `cancel()` / 教师覆盖的隐患。

### 4.2 单元占用算法（伪代码，直接可落地）

```java
// 提交申请：只读检查，不写 slot
List<SlotUnit> units = SlotUnit.of(startTime, endTime);   // 校验对齐 / 1..16 / 提前 ≤7 天
assertNoOverlap(roomId, units);                            // 查 slot 表，命中即 REJECTED_BASIC
// 注意：查 t_reservation 中"待审批且同单元"不算冲突，只作提示

// 批准：写 slot，唯一键仲裁
try {
    for (SlotUnit u : units) slotMapper.insert(reservationId, roomId, u.date(), u.index());
} catch (DuplicateKeyException e) {
    tx.rollback();                                          // 任一元冲突整体回滚
    return "conflict";
}
```

关键点：`assertNoOverlap` 与插入之间**存在窗口**，但唯一键保证了最坏结果是"批准失败并提示重选"，而不是"重复占用"。这是文档"任一元冲突即整体回滚"的直接实现，不需要分布式锁。

### 5.2 三层规则引擎

**判定顺序（固化 D3）**：

```
1. 基础规则（BASIC，代码内置、只读、每次必检）
   任一不满足 → REJECT（附原因），终止
2. 强制转人工条件（先于自动通过判断，从严优先）
   - attendeeCount >= manualReviewHeadcount(默认 5)
   - 房间或时段被管理员冻结
   - 信用分 < 70 且未填 purpose
   → 命中即 FORCE_MANUAL，终止
3. 附加规则自动通过（EXTRA）
   - 信用分 >= autoApproveCredit(默认 90)
   - 信用分 70..89 且 时长 <= midMaxDuration(默认 120min)
   - 当日自动通过笔数 < dailyAutoLimit(默认 3)
   - 连续占用 <= maxContinuous(默认 240min)
   → 全部满足即 AUTO_APPROVE；否则 FORCE_MANUAL
4. 教师路径（独立分支，不进上述流程）
   教师申请：单元无冲突 → 直接 APPROVED；与其他教师冲突 → REJECT；
            与学生冲突且该学生预约未开始 → 覆盖（CANCELED + TEACHER_OVERRIDE）
```

**实现形式（明确反对通用 DSL）**：

```java
public interface BasicRule {          // 代码内置，@Component，注册进 List
    String code();                    // "B01_ACCOUNT_ACTIVE"
    Optional<RuleOutcome> check(RuleContext ctx);
}

public class RuleEngine {
    public RuleOutcome evaluate(RuleContext ctx);   // 依序跑 basic → forced → extra
}
```

- 基础规则 6 条，每条一个类，一个单测：`B01 账号有效并角色匹配` / `B02 时段对齐与时长` / `B03 人数 1..容量` / `B04 单元不重叠` / `B05 信用分 ≥60` / `B06 无未处理严重违规`。
- 附加规则参数全部来自 `t_rule_config`，**只有参数、没有表达式**。要加新参数就加一行配置 + 一个 if，绝不引入脚本引擎（16 周内不可维护、无法测试）。
- 每次判定把 `rule_version_id` + `hit_rule_codes` 写进 `t_reservation`，申诉时直接展示依据（文档 3.2.2 要求"历史审核按当时的版本记录"）。

**规则发布流程**：后台改参数 → 生成 `t_rule_version`（version_no 自增，`effective_from` 默认 now，可设未来）→ 写 `t_rule_config` 快照。旧预约的 `rule_version_id` 不变，因此改参数不影响历史判定。

### 5.3 信用分

- 账本优先：`score` 是缓存，任何调整都先写 `t_credit_log` 再重算 `score = clamp(100 + SUM(delta), 0, 100)`，同一事务。
- `uk_res_reason (reservation_id, reason_code)` 从库层挡住重复扣分（文档要求"测试重复扣分与复核回退"）。
- 30 日内再犯加倍：查该用户 30 天内是否已有同 `reason_code` 的负向流水，有则本次 `delta *= 2`，并额外写 `reason_code=REPEAT_DOUBLE` 的注记行（`delta=0`，便于审计）。
- 三项正向加分：`ON_TIME_CHECKIN +2`（签到成功且未爽约）、`CLEAN_30D +5`（定时任务每日扫一次，30 天内无负向流水且至少有 1 笔正常结束）、`APPEAL_REVOKE`（申诉成立时对冲原扣分）。
- `<60` 不再自动通过：由基础规则 `B05` 直接拒绝，而不是"转人工"（文档表 3-3 写的是"低于 60 分不再自动通过，改由人工审核"——**这里有歧义**：基础规则说"信用分不低于 60"不满足即拒绝，表 3-3 末行说"低于 60 改由人工审核"。两者冲突。本计划取**从严**：基础规则拒绝（因为基础规则章节明确"任一条不满足即拒绝"），并在待确认清单 Q3 中标出）。

### 5.4 申诉

- 提交入口：`我的预约` 与 `信用分` 两个页面均可，`target_type` 区分。
- 唯一性：`uk_user_target` 保证"7 日内提交一次"；`7 日` 用 `created_at` 与原判定的 `closed_at` 比较，超期直接拒绝并在页面提示。
- 时限：`due_at = created_at + 3 工作日`（跳过周六日，不做节假日表）。到期由定时任务标红，不自动改判——文档只要求"3 个工作日内给出书面结论"，不要求超时自动处理。
- 复核人 ≠ 原审核人：`appealService.decide(id, reviewerId)` 内校验 `target.reservation.approvedBy == reviewerId` → 拒绝并提示"不得自审"。
- 结论类型：`UPHELD`（维持）/ `REVOKED`（撤销扣分）/ `PARTIAL`（纠正记录但维持扣分）。
- **不恢复单元**：`REVOKED` 只写 `credit_log(+delta)`；若用户仍需要房间，走"按剩余单元优先重建"——即生成一条新的 `待审批` 申请并带 `decision_path=APPEAL_REBUILD`，由管理员优先批准。这条要在页面上明说，避免用户以为申诉能拿回房间。

## 6. 设备侧与 MQTT 契约

### 6.1 主题

| 主题 | 方向 | QoS | Retained | 说明 |
|---|---|---|---|---|
| `room/{deviceCode}/snapshot` | S→D | 1 | **是** | 带 `version` 与 `expiresAt` 的业务快照（当前预约码/剩余时间/状态） |
| `room/{deviceCode}/cmd` | S→D | 1 | **否** | 一次性指令（UNLOCK/BUZZ/CLEAR） |
| `room/{deviceCode}/ack` | D→S | 1 | 否 | 指令回执 |
| `room/{deviceCode}/heartbeat` | D→S | 0 | 否 | 30 秒一次 |
| `room/{deviceCode}/event` | D→S | 1 | 否 | 手动释放、故障、掉电恢复 |

ACL：设备账号只能 `readwrite room/{自己的 deviceCode}/#`；后端账号可 `room/+/#`。**禁止** `#` 通配给设备。

### 6.2 消息信封

```json
{
  "v": 1,
  "msgId": "0f3c...-uuid",
  "type": "UNLOCK",
  "deviceCode": "ROOM-01",
  "reservationId": 42,
  "issuedAt": "2026-10-21T10:03:12",
  "expiresAt": "2026-10-21T10:03:42",
  "payload": { "pulseMs": 3000, "reason": "FIRST_CHECKIN" },
  "hmac": "b1e4..."
}
```

`hmac = HMAC-SHA256(device.secret, canonical(v|msgId|type|deviceCode|reservationId|issuedAt|expiresAt|payload))`

设备端校验顺序（必须与文档 3.2.3 的"校验归属、有效期与重复请求"逐条对应）：
1. `deviceCode` 匹配自身 → 否则丢弃
2. `hmac` 校验 → 否则丢弃并记事件
3. `expiresAt > now` → 否则丢弃（**旧指令不得触发开锁**，对应 C12）
4. `msgId` 在最近 16 条去重表内 → 丢弃（QoS1 允许重复）
5. `reservationId` 与当前显示的预约一致 → 否则丢弃（防止跨预约误开）
6. 执行 + 回执

### 6.3 心跳与在线判定

- 设备每 30 秒发 `heartbeat`（含 `uptime`、`rssi`、`lastCmdId`）。
- 后端 `HeartbeatWatchdog` 每 30 秒扫描：`now - last_heartbeat_at > 90s` → `online=0`，页面显示"设备离线"，**但不阻止**业务状态流转（签到仍可成功，只是立刻提示"门禁离线，请用机械释放杆"）。
- 文档 4.1 T4 要求"重连校验快照"：设备重连后先订阅 `snapshot`，用 `version` 比较决定是否覆盖屏幕。

### 6.4 设备模拟器（硬件未到货期间的交付物）

### 7.3 主预约界面：多房间横向排期板（替代甘特图）

沿用 2026-10-20 已定的技术决策（CSS Grid + 15 分钟列 + 房间行），只把数据源从"区间条"换成"单元格"。**2 间房 × 56 单元 = 112 格**，DOM 量极小，不需要虚拟化。

```
            08:00   09:00   10:00   11:00  ...        22:00
          ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
研讨室A 6人│▢ │▢ │▣ │▣ │▣ │▢ │▢ │◐ │◐ │▢ │▢ │  │  │  │▢ │
          ├──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┤
研讨室B 6人│▢ │▢ │▢ │▢ │▢ │▢ │▣ │▣ │▣ │▣ │▢ │  │  │  │▢ │
          └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘
  ▢ 空闲可选   ▣ 已占用   ◐ 仅待审申请（仍可选）   ▤ 我自己的

  筛选：[日期 2026-10-21] [人数 4] [设备：白板]      → 不满足的房间行整体置灰
  已选：研讨室A  09:15–10:15（4 格 / 1 小时）
  人数 [ 4 ]  用途 [__________]        [ 提交申请 ]
```

| 项 | 决策 |
|---|---|
| 渲染 | CSS Grid；房间为行、单元为列；跨单元格直接用 `grid-column: a / b`，不做像素↔时间反算 |
| 列头 | 每 30 分钟标注一次，每 4 格（1 小时）加粗分隔线 |
| 移动端 | **单视图横向滚动 + 房间列 sticky**（不做双视图，避免两套渲染） |
| 选择 | 第一次点 = 起点格，第二次点 = 终点格；必须在**同一房间行**内；终点早于起点自动交换 |
| 约束 | 连续且 `1 ≤ 格数 ≤ 16`；跨过 `OCCUPIED` 格 → 按钮变红禁用；跨过 `PENDING_ONLY` → 按钮变橙并提示"已有 N 人申请，需管理员审核" |
| "按需求找房间" | 就是这张板 + 筛选条：人数 > 容量、缺所需设备的房间行置灰，**不需要单独的筛选结果页**（避免上线即废弃） |
| 可操作性 | 每格返回 `actionable` 布尔，由后端算，前端**禁止**按 role 自行推导能否覆盖 |
| 旧入口 | `/reservation/new?roomId=X` → 302 到 `/reservation/board?date=今天&focus=X`；`reservation-new.js` 与 `reservation-new.html` 显式删除，不留死代码 |

> 顺带修掉一个现存缺陷：`findByRoomAndDate` 只查 `status=1`，而 `findConflicting` 判 `IN (0,1)`，导致"板上看不见、提交却被拒"。新模型下待审批**不占单元**，板面天然诚实——`◐` 格明确标注"仍可选"，语义与后端一致。
