# 5 分钟演示脚本（P8-T03）

> 目标：5 分钟内讲清"改了什么、为什么这么改、软硬件怎么串起来的"。
> 逐条验收见 [`acceptance.md`](acceptance.md)，技术细节见 [`重构改造计划.md`](重构改造计划.md)。

## 演示前 10 分钟准备

```bash
# 1) 复位数据
mysql -u root -p db02 < sql/init-demo.sql

# 2) 以 MQTT 全链路模式启动（控制台能看到 [LOCK] / [SIM]）
./mvnw spring-boot:run -Dspring-boot.run.profiles=local,mqtt-demo
```

打开两个浏览器窗口：

- 窗口 A：`student01 / demo123`
- 窗口 B（无痕）：`admin01 / demo123`

> ⚠️ **时间窗口是硬约束**：签到只能在预约开始后的 5 分钟内完成。
> 演示前 2 分钟先用 student01 在排期板上约**下一个整刻钟**的 2 格（30 分钟），
> 整刻钟一到立刻签到。如果错过了，就把它当成"讲清楚为什么这样设计"的机会（见文末兜底）。

## 0:00–0:40 先讲问题

一句话开场：

> "原来的系统有三个问题：同一时段只要有人提交申请，别人就约不了，但那个申请可能根本没被批准；
> 时段在前端吸附、后端不校验；签到靠自觉，代签和爽约管不住。"

对应到界面上就是三处改动：待审批不占单元、后端强校验、门禁开锁 + 信用分。

## 0:40–2:00 排期板提交（核心）

窗口 A 进入 **预约排期**：

1. 指出界面结构：一行一间房，横向 56 格 = 08:00–22:00 每 15 分钟一格。
2. 讲图例：**绿色可约 / 黄色虚线=有人待审批（仍可约）/ 灰色=已占用 / 深绿=我的**。
   > "这格是黄虚线，说明有人申请了但还没批。**你仍然可以约**——因为待审批不占单元。"
3. 点第一格 → 点第二格，底部显示 `10:00–10:30，2 个单元（30 分钟）`。
4. 人数填 3，提交 → 提示"预约已生效，签到码 1234"（信用 100 分自动通过）。
5. 再演示一次**转人工**：人数填 5，提交 → "申请已提交，等待管理员审核"。
   > "人数达到阈值一律转人工，这条优先于'信用分 90 自动通过'。"

## 2:00–3:00 审批与"为什么进人工"

窗口 B 进入 **审批管理**：

1. 指出表格新增的 **"为什么进人工"** 列：`E01_HEADCOUNT`。
   > "管理员不用猜这笔为什么没自动通过——判定路径和命中规则都写在单据上。"
2. 点批准 → 提示签到码。**控制台此时应出现 `[SCREEN]` 相关日志**（屏幕已推送快照）。
3. 顺便说明：如果这时该时段已被别人占住，批准会失败并整体回滚，不会出现"状态改了但没占上单元"。

## 3:00–3:40 签到与开门（软硬件）

窗口 A 进入 **我的预约**，在到点的那笔上点 **签到**：

1. 输入屏幕上的 4 位码（演示环境为控制台/页面显示的码）。
2. 签到成功 → **控制台出现**：

```
[SIM] 设备模拟器已启动：device=ROOM-A-01
开锁指令已发布：device=ROOM-A-01 msgId=... expiresAt=...
[LOCK] PULSE 3000ms  reason=FIRST_CHECKIN
收到回执：device=ROOM-A-01 msgId=... result=OK
```

3. 讲这三行：
   > "指令带 HMAC 签名、30 秒有效期、唯一 msgId。设备端要验签、验过期、验去重、
   > 还要验预约号与屏幕当前显示的是同一笔——五步全过才开锁。"
4. 再点一次 **开门**（已签到状态）→ 第二笔指令，载荷标 `reason=REOPEN`。

## 3:40–4:20 信用分与申诉

1. 窗口 A 进入 **我的信用分**：分数、三档阈值的含义、流水。
2. 讲扣分规则：爽约 −10、30 日内再犯加倍、按时结束 +2、30 日无爽约 +5。
3. （可选）让 admin 在预约详情页点"认定违规使用 −20"，刷新信用页看到扣分。
4. 点 **申诉** → 填说明提交 → 窗口 B 的 **申诉复核** 里出现工单。
   > "复核人不能是申请人，也不能是原审核人，系统会拦。"

## 4:20–5:00 规则可调与设备状态

1. 窗口 B **审核规则**：8 个参数 + 版本历史。
   > "每次保存生成新版本，已判定的预约仍按当时的版本，改参数不会篡改历史。"
2. **设备管理**：在线状态、最近指令（ACKED/SENT/EXPIRED）、测试开锁。
   > "在线状态由心跳决定，不能手工改；这里也会如实显示当前是 `log` 还是 `mqtt` 通道。"

## 收尾一句话

> "核心是三条：**待审批不占单元**让同一时段能并存多笔申请；**单元唯一键**让并发批准不会重复占用；
> **一次性指令 + HMAC** 让门禁不会重放、不会误开。"

---

## 兜底：如果错过了签到窗口

不要硬演。直接把页面上的提示念出来：

> "提示是『签到已截止（须在开始后 5 分钟内完成）』——这不是 bug，是验收项 AC-14。
> 5 分钟窗口是为了让爽约能被认定：如果允许随时签到，'占着不来'就没有成本。"

然后走 `2:00` 之后的审批、信用、规则部分，最后回到排期板补一次"约整刻钟"的现场签到。

## 可能被问到的问题（备答）

| 问题 | 回答要点 |
|---|---|
| 为什么不用 Redis 锁？ | 单元唯一键本身就是仲裁，库层保证比分布式锁更简单可靠；撞键直接回滚，最坏结果是"批准失败"而不是"重复占用"。 |
| 待审批不占单元，会不会被抢？ | 会——所以待审批状态在排期板上显示为黄色虚线，管理员批准时会重检占用，冲突则让申请人重选。 |
| 签到码被人看到怎么办？ | 码只在待签到阶段显示在屏幕上，签到后屏幕切"已签到"且码不再下发；再次开门走账号认证，不需要码。 |
| 开锁失败会不会扣分？ | 不会。签到先落库，开锁失败只提示"请联系管理员或使用机械释放杆"，签到结果不回滚。 |
| 申诉赢了能不能拿回房间？ | 不能。时段可能已被别人订走，恢复会制造重叠占用；只撤销扣分，需要房间请重新预约。 |
